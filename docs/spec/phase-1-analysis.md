### Introduced by `/spec`

| ID | Area | Assumption | Rationale | Impact if wrong | HLD impact |
|---|---|---|---|---|---|
| SA-01 | Toolchain | The project constants are those of HLD `05-tech-stack.md`: Rust 2024 edition; the toolchain is pinned in `rust-toolchain.toml` to the stable release current at Phase 1 scaffolding, never older than 1.85.0 (the first release supporting the 2024 edition). | No `project-constants` rule exists; the HLD fixes the stack. | Every crate spec changes if the language or edition changes. | — |
| SA-02 | Toolchain | Every third-party crate is declared once in the root `Cargo.toml` `[workspace.dependencies]` with an exact `=` version, chosen as the latest release on crates.io at Phase 1 scaffolding; `Cargo.lock` is committed. | Reproducible `proved` results and builds (HLD risk: Z3/LLVM churn). | Unpinned upgrades change solver behaviour silently. | — |
| SA-03 | Platforms | v1 supports exactly two host targets: `x86_64-unknown-linux-gnu` and `aarch64-apple-darwin`. Z3 is a system install, major version 4, minor ≥ 12, linked through the `z3` crate without its bundled-build feature. LLVM is a system install of major version 18, used through `inkwell` with its `llvm18-0` feature. | Settles OQ-16 and OQ-17. Two targets cover the stated developer workstation and CI host (A-5); system installs keep `cprimec` builds fast. | A third target adds a CI leg and calling-convention tests for JIT and AOT. | E-01 (ADR-028) |
| SA-04 | Transport | `cprimed` speaks JSON-RPC 2.0 over its own standard input and standard output only. Framing is one UTF-8 JSON object per line (`\n`-terminated, no embedded raw newlines). The same stream accepts the three C′ methods and the MCP methods `initialize`, `notifications/initialized`, `tools/list`, `tools/call` and `ping`. No socket is opened. | Settles OQ-11. stdio is the transport every MCP client supports; it confines access to the parent program, which satisfies A-1 without authentication. | Several agents cannot share one daemon; each agent host starts its own (blocked from the same project by SA-05). | E-02 (ADR-029) |
| SA-05 | Concurrency | Each `cprimed` serves one client (its parent, over stdio) and executes that client's requests strictly one at a time in arrival order. Any number of `cprimed` instances may run on one project, one per agent session. Writes of accepted implementations are serialised by an exclusive advisory lock on `<root>/.cprime/lock`, held only while writing (`cprime-daemon` §H). Under that lock, the daemon compares the on-disk metadata of the target `.opq` and of every `.opq` its verification read with the values its sync recorded at the start of the request; any difference refuses the write with `-32005` (`implementation changed on disk`) and nothing is written. | Settles OQ-25 and amends A-3 (user decision, 2025-12-20: concurrent agent sessions on one project are common). Disk is authoritative (ADR-003) and re-read before every request (SA-06), and verification is modular (ADR-033), so sessions can only collide on writes to the same files; the check turns a silent overwrite into an explicit conflict. | Each session's `cprimed` keeps its own Salsa cache and solver instances, so memory grows with the number of sessions. A conflict discards the verification work of the refused submission. | E-14 (A-3 amended) |
| SA-06 | Source sync | Before executing each request, `cprimed` walks the project root, compares every `.cprime`, `.opq` and `cprime.toml` file's (modification time, byte length) with its last-seen value, re-reads changed or new files into the Salsa inputs, and removes inputs for deleted files. Directories named `.cprime`, `target` and any directory whose name starts with `.` are skipped. | Settles OQ-12. Needs no file-watching dependency and is deterministic: every request sees the files as they are when it starts. | Large projects pay a walk per request; reported separately as `timings_us.sync`, outside the T0 budget. | E-03 (ADR-030) |
| SA-07 | Persistence | An accepted `.opq` file begins with one acceptance header comment line: `;; cprime-accepted v1 context=<64 lower-case hex> evidence=<proved\|tested> assumed=<comma-separated qualified operation names, or ->`. `context` is the verification context hash (glossary). An implementation is **stale** when the recorded hash differs from the hash recomputed from current sources. Stale implementations are reported by `get_context` and refused by release builds; they are not re-verified automatically. | Settles OQ-13 (mark stale, no automatic re-verification) and amends A-16 (the evidence level is now stored in the header). | Without the header, an edited spec silently leaves old code marked as fine. | E-04 (ADR-031), E-15 (A-16 amended) |
| SA-08 | Runtime | The project-specific runtime build produces two artefacts from one generated Cargo package at `<root>/.cprime/runtime/`: the project's own `cprimed` executable at `<root>/.cprime/bin/cprimed` (the `cprime-daemon` library plus every provider, statically linked) and the static library `<root>/.cprime/lib/libcprime_runtime.a` (the `cprime-provider` runtime support plus every provider) for release linking. The command `cprimec daemon` is the launcher an agent host runs: it rebuilds the runtime when `<root>/.cprime/runtime.fingerprint` does not match, then replaces itself with `.cprime/bin/cprimed` with standard input and output inherited. | Settles OQ-22 (rebuild at launch). Static linking into a project-specific `cprimed` is the only way JIT code can call third-party providers without dynamic loading, which is a non-goal. | If dynamic loading were acceptable, one generic `cprimed` binary would suffice. | E-05 (ADR-032), E-10, E-11 |
| SA-09 | Crates | The workspace gains one crate, `cprime-cli` (binary `cprimec`). `cprime-daemon` is a library with a `run` entry function and no binary of its own. The four built-in providers are four crates under `providers/`: `cprime-host-crypto`, `cprime-host-clock`, `cprime-host-random`, `cprime-host-log`. Built-in providers are linked into every project runtime without a manifest entry. | Settles the `cprimec` half of OQ-15; follows from SA-08. | — | E-10 |
| SA-10 | Manifest and configuration | The project manifest is `<root>/cprime.toml`. Its presence marks the project root. It holds the provider list (`[[providers]]`) and the configuration sections `[limits]`, `[verify]`, `[fuzz]`, `[log]`, `[runtime]`. Command-line flags override file values; nothing is read from environment variables. | Settles OQ-24; keeps A-10 (file and flags, read once at start). | — | E-12 |
| SA-11 | Modules | No imports and no visibility markers in v1; every definition is public. Module `A::B` lives in `<root>/a/b.cprime`; each path segment is converted from UpperCamelCase to snake_case. Implementations of module `A::B` live in `<root>/a/b/<spec>.opq`. Names in both surfaces resolve in this order: local binding, definition in the current module, prelude, absolute path from the project root. | Settles OQ-29. Matches the concept example, in which `.opq` writes `SessionToken` and `CryptoCap::hmac_sha256` relative to module `Auth`. | HLD `08-interfaces.md` says names in `.opq` are always fully qualified; the concept example contradicts it, so the HLD sentence is corrected. | E-12 |
| SA-12 | Language | No first-class functions in v1. A function name may appear only in call position. `Type::Fn` describes spec and entry signatures only. | Settles OQ-30; keeps ADR-023 and ADR-024 simple. | — | E-16 |
| SA-13 | Ownership | `cprime-types` owns `UnconstrainedOutput` and the sum-type completeness rule of ADR-026. | Settles OQ-19: `cprime-types` holds the typed contract and the result type. | — | E-11 |
| SA-14 | Fuzzing | When T3 cannot execute the configured iteration count of `requires`-satisfying inputs within its time budget (rejection-sampling starvation, a resource limit, a callee without an accepted implementation, a provider panic while a contract is evaluated, or a provider call that does not return within `verify.provider_wait_ms` of the deadline; D41, D42), the submission is rejected with `VerificationInconclusive`, tier `T3`, and a `reason` string. | Settles OQ-21; fails closed, adds no diagnostic kind. | Specs with very tight `requires` cannot use `assurance tested`. | E-12 |
| SA-15 | Scope | v1 has no request cancellation (OQ-28), does not persist SMT-LIB obligations (OQ-26), and does not support provider-supplied contracts (OQ-27). The licence review is deferred to Phase 5 (OQ-23); the provider inventory records each crate's licence expression to support it. | Recommended answers in the HLD; budgets bound every request (≤ 2 s T2 + ≤ 5 s T3 by default). | — | E-16 |
| SA-16 | Release binary | A release binary reads one JSON object from standard input whose keys are the entry point's parameter names, writes the entry point's result to standard output as one JSON value followed by `\n`, and exits with the codes defined in `phase-2-architecture.md` §2C `ExitCode`. This applies to batch entries; a server binary (SA-65) reads no standard input and runs until stopped. Values use the Value JSON encoding. | Settles OQ-18. | An embedding API would need a C header and ABI promises. | E-12 |
| SA-17 | Encoding | C′ values cross every JSON boundary (counterexamples, release-binary I/O) in the **Value JSON encoding**: `Unit` → `null`; `Bool` → `true`/`false`; `U8`, `U64`, `I64` → JSON integer; `Bytes` and `FixedBytes[N]` → string `"0x"` followed by lower-case hex; `Vec[T]` → array; struct → object keyed by field name in declaration order; sum value → object with exactly one key, the variant name, whose value is the variant's field object (`{}` for a field-less variant). | One encoding for agents and release users. `serde_json` represents `u64` and `i64` exactly. | JavaScript clients lose precision above 2^53; agents read the text, not a JavaScript number. | — |
| SA-18 | Verification | Verification is modular. A call from an implementation to a spec is modelled by the callee's contract, not its body. Each call site generates a **call-precondition obligation**: the callee's `requires`, instantiated with the call arguments, under the caller's `requires` and path condition. A counterexample yields `ContractViolation` whose `clause` is `requires of <Callee>: <clause text>`. | Without it, a caller could invoke a callee outside its contract and inherit `ensures` facts that do not hold. | — | E-06 (ADR-033), E-13 |
| SA-19 | Contracts | Contract expressions use mathematical integers (no overflow), are pure, and follow the definedness rule (glossary). `&&`, `\|\|` and `==>` short-circuit left to right. Variant tests are written `e is V`; variant-field access is written `e.V.f`. The SMT encoder and the fuzzing evaluator implement the same semantics. | Settles the gate item "operational meaning of contract expressions" and the variant-test syntax of ADR-026. | Divergent semantics between Z3 and fuzzing would make `tested` and `proved` disagree. | E-13 |
| SA-20 | Termination | A recursive component is a strongly connected component of the call graph over (accepted implementations ∪ the candidate). Every member's `decreases` tuple must have the same length. One `decreases` obligation is generated **per call edge** inside the component, including call edges inside already-accepted members, which are re-checked against the candidate's measure. | Settles ADR-024's obligation granularity; closes the hole where a later submission closes a cycle over an earlier acceptance. | — | — |
| SA-21 | Runtime limits | The CPU-time limit is enforced by **fuel** in the IR interpreter and JIT (one unit per function entry; recursion is the only iteration, so fuel bounds work), and by `setrlimit(RLIMIT_CPU)` in release binaries. The memory limit is enforced by the runtime allocator in `cprime-provider`, which counts live bytes. Exceeding either aborts with a distinct exit code. Server binaries (ADR-051) set no `RLIMIT_CPU`: each server task's work is bounded by fuel (`limits.request_fuel`, one unit per function entry), its depth by `limits.max_call_depth`, and all tasks share `limits.memory_bytes`; exceeding any of them ends only that task. | Settles how ADR-016 limits are enforced. JIT code running inside `cprimed` cannot be pre-empted by a timer. | — | — |
| SA-22 | Language | The language gains a `Unit` type (written `Unit`, value `()` in `.opq`, `null` in JSON). `Unit` joins the provider boundary types. | Gate item "IR additions: a unit type"; `host::Log` operations return nothing. | — | E-12 |
| SA-23 | Prelude | The prelude is exactly: types `Hash = FixedBytes[32]`, `enum Result[T, E] { Ok { value T }; Err { error E } }`, `enum Option[T] { Some { value T }; None }`; functions `len`, `index`, `++`, `u64_be`, `push`, `slice`, `to_bytes`; constants `U8::MAX`, `U64::MAX`, `I64::MIN`, `I64::MAX`; the built-in capability `Diverge`. Signatures are in `phase-2-architecture.md` §2C `Prelude`. | Gate item "further prelude members"; the minimum set that lets recursion build vectors and byte strings. | Corpus tasks may need more members; additions are a Branch B change. | E-13 |
| SA-24 | Verification | T2 runs obligations on `verify.solver_threads` parallel Z3 contexts (default: the smaller of 4 and the host's available parallelism). Scheduling order is fixed: trap-site obligations (IR order), call-precondition obligations (IR order), `decreases` obligations (IR order), `ensures` obligations (clause order). When the per-submission budget is spent, running obligations are interrupted and unstarted ones are cut off; both count as `unknown`. | Settles ADR-025's parallelism and cut-off order. Trap and precondition obligations are usually the cheapest. | — | — |
| SA-25 | Memory model | Every struct and sum value is heap-allocated and reference counted, including those with only scalar fields. All values are represented as one 64-bit word: scalars zero- or sign-extended, `Unit` as 0, heap values as a pointer. | One value representation for interpreter, JIT, AOT and the provider ABI. | Scalar-only structs pay an allocation; Phase 5 benchmarks measure it. | E-11 |
| SA-26 | Logging | `cprimed` and `cprimec` write one JSON object per line to standard error. Levels: `error`, `warn`, `info` (default), `debug`, `trace`. Submitted source and counterexample values are written only at `trace`. | Refines A-4. | — | — |
| SA-27 | Shutdown | End of standard input: `cprimed` finishes the request in progress, writes its reply, and exits 0. `SIGINT` or `SIGTERM`: `cprimed` abandons the request in progress without replying and exits 0 within 200 ms; an atomic rename already completed stays on disk. | Refines A-14 and the HLD graceful-shutdown stance. | — | — |
| SA-28 | Hashing | Canonical serialisation of every definition begins with the ASCII domain tag `cprime.def.v1` followed by one zero byte. A change of canonical form bumps the tag to `v2`; the acceptance header's `v1` names the header format. | Settles OQ-14 for v1: a hash-scheme version, no per-file language marker. | — | E-16 |
| SA-29 | Entry point | An `entry` is implemented by an `.opq` file like a spec (`<module-dir>/<entry>.opq`), has no `requires`/`ensures`, generates only trap-site and `decreases` obligations, and is verified under `assurance proved`. A project declares at most one `entry`; a release build requires exactly one. `bind` declarations are legal only in the module that declares the `entry`. | The HLD does not say how an entry body is written. | — | E-12 |
| SA-30 | Fuzzing | During T3, a `deterministic` operation of a capability that has a `bind` calls the bound provider; a `deterministic` operation without a `bind` is replaced by a memoising stub (equal arguments, equal result within one T3 run); every other operation is replaced by a stub returning generator-chosen values. The double-call determinism probe runs only on bound operations. A bound `deterministic` operation is called through a memoising wrapper whose memo the contract evaluator shares, so a contract calls the provider only for argument tuples the program did not already use (D42, ADR-054). | Makes fuzzing possible before any entry point exists while staying faithful to the uninterpreted-function model. | — | — |
| SA-31 | Crates | `cprime-core` owns the untyped AST, the typed AST, the IR, hashing, the namespace table, name resolution, the Salsa database trait and the context query. `cprime-types` owns type checking, monomorphisation and lowering of the typed AST to IR. `cprime-codegen` owns the IR interpreter (the reference oracle), the Cranelift JIT and the LLVM AOT back end. `cprime-provider` owns the runtime ABI (heap layout, allocator, reference-count operations, trap entry) in addition to the SDK. | Every crate in the HLD graph keeps its dependency edges: verification consumes typed contracts from `cprime-core`, not from `cprime-types`. | — | E-11 |
| SA-32 | Diagnostics | Every v1 diagnostic has severity `error`, except `VacuityUnknown`, whose severity is `note`; a `note` never affects acceptance (D37, ADR-052). Node ids number the nodes of the submitted `.opq` syntax tree in pre-order from 0 (the `impl` form). A diagnostic about the spec rather than the submission carries `node: 0` and a `span` pointing into the `.cprime` file. | The HLD fixes integer node ids but not the numbering. | — | — |
| SA-33 | Cross-cutting | Authentication, tracing of `cprimed` itself, rate limiting, pagination, CORS, health checks and database migrations are out of scope in v1, for the reasons recorded in HLD `07-cross-cutting.md`. Each receives an `N/A` entry in `phase-4-cross-cutting.md`. Traces of programs are specified by D22–D28 (ADR-047, ADR-048). | Required by the specgen concern list. | — | — |
| SA-34 | Defaults | Configuration defaults: `verify.obligation_timeout_ms` 250; `verify.submission_budget_ms` 2000; `fuzz.iterations` 10000; `fuzz.time_budget_ms` 5000; `fuzz.call_fuel` 10,000,000; `fuzz.call_memory_bytes` 67,108,864 (64 MiB); `limits.cpu_time_ms` 10000; `limits.memory_bytes` 1,073,741,824 (1 GiB); `log.level` `info`. | Budget values come from HLD G5; the limits are conservative defaults. | — | — |
| SA-35 | Built-in providers | Built-in operations (C′ signatures in `phase-2-architecture.md` §2C): `host::Crypto` — `sha256`, `hmac_sha256`, `blake3` (all `deterministic`); `host::Clock` — `now_unix_seconds`, `monotonic_nanos`; `host::Random` — `random_bytes`, `random_u64`; `host::Log` — `info`, `warn`, `error`. | SA-37 | Hashing | Spec parameter names, the `ensures` binder, local names, spans, comments, contract source text and the acceptance header are excluded from `DefId`s. | SA-39 | Types | A type with no finite values (`struct T { t T }`) is `TypeMismatch` (type-level enforcement of ADR-023). | SA-42 | Codegen | The interpreter runs on an explicit frame stack and is never used for fuzzing; a stubbed operation in the interpreter traps `Unreachable`. | SA-43 | Verification | Each obligation is one SMT-LIB 2 script in its own Z3 context per worker thread; cut-off uses Z3 interruption. | SA-45 | Daemon | `cprimed` flags `--project`, `--config`, `--log-level`, `--describe-providers`, `--version`; it requires `cprime.toml` in the given directory. ## 1C Glossary

Terms from HLD `00-overview.md` apply unchanged. Terms below are new or sharpened by `/spec`; rows marked † are proposed for the HLD glossary (edit E-07).

| Term | Definition | Example |
|---|---|---|
| C′ † | The language and toolchain this spec set describes; pronounced "C-prime", ASCII `C'`, identifier stem `cprime`. Named "Pact" before ADR-049. | `cprimec build --release` |
| Contract † | A specification a person approves: types, capabilities, `requires` and `ensures`, written in a `.cprime` file (ADR-046, ADR-050). Called a "pact" before ADR-050. | `auth.cprime` |
| Statement terminator † | The end-of-statement marker (`TERM`) the `.cprime` lexer inserts at a newline after an identifier, literal, `)`, `]`, `}`, `proved`, `tested` or `variant`; a line ending in an operator or `,` continues (ADR-050). | `requires user_id > 0` ends at its newline |

| Server † | A release program declared by a `server` item; it runs until stopped and serves requests (ADR-051). | `server Api { handler Api::handle; transport acme::HttpTransport }` |

| Acceptance header † | First line of an accepted `.opq`, recording format version, verification context hash, evidence level and assumed provider operations. | `;; cprime-accepted v1 context=9f…e1 evidence=proved assumed=Auth::CryptoCap::hmac_sha256` |

| Stale implementation † | An accepted implementation whose recorded verification context hash differs from the current one. | `auth/generate_token.opq` after `generate_token`'s `ensures` is edited |
| Call-precondition obligation † | Proof obligation that a call site satisfies the callee spec's `requires`. | `requires of Math::div_exact: d > 0` |
| Definedness rule † | A contract clause holds only if it is defined and true. | Variant test † | Contract expression `e is V`, true when sum value `e` is variant `V`. | `result is Err` |
| Fuel † | Count of function entries an interpreted or JIT-compiled call may perform before it aborts with the CPU-time limit. | `fuzz.call_fuel = 10000000` |
| Call-depth limit † | Maximum nesting of C′ calls before a call traps `StackLimit`. | `limits.max_call_depth = 100000` |
| Launcher † | `cprimec daemon`: checks the runtime fingerprint, rebuilds the runtime if stale, then replaces itself with the project's `cprimed`. | Agent host config: `cprimec daemon --project .` |
| Runtime fingerprint † | Blake3 hash over the `cprimec` version string, the `[[providers]]` entries of `cprime.toml`, `runtime.cprime_source`, the `Cargo.toml` and `src/` tree of every path provider, and the `Cargo.lock` of the generated runtime package. | `.cprime/runtime.fingerprint` |
| Value JSON encoding † | The JSON form of C′ values at every JSON boundary (SA-17). | `{"Ok": {"value": 3}}` |
| Typed AST | Output of `cprime-types`: the AST with resolved names, monomorphised types and per-node types. Consumed by `cprime-effects`, lowering and `cprime-verify`. | `TExpr { node, ty, kind }` |
| Intrinsic † | A prelude function implemented by the runtime, not by a spec: `len`, `index`, `++`, `u64_be`, `push`, `slice`, `to_bytes`. | `IntrinsicOp::U64Be` |
| `Unit` † | Type with one value; the result of operations performed only for their effect. | `host::Log::info` returns `Unit` |
| Recursive component | A strongly connected component of the call graph with at least one edge; the unit of ADR-024's shared measure. | `{Math::even, Math::odd}` |
| Future-reserved word † | A word with no v1 meaning that v1 rejects as a name, so a later version can give it one (ADR-043, SA-49). | `loop` in `.opq` |
| Reserved type name † | A type name v1 forbids declaring because a later built-in type will claim it (ADR-043, SA-49). | `Str` |
| Parallel map † | The `.opq` form `(par_map S xs)`: applies spec `S` to every element of `xs`; parallel in release binaries, sequential everywhere else (ADR-044). | `(par_map Auth::verify_one tokens)` |
| Worker † | A thread a release binary uses for one contiguous chunk of a parallel map. | — |
| Worker context † | The `RtContext` of a worker (`mode` 2): its own heap, depth counted from the caller, memory counted against the shared limit. | — |
| Thread-safe provider † | A provider whose `ProviderDecl` sets `thread_safe: true`, so `par_map` may call its operations from several workers (ADR-045). | `host::Crypto` |
| Witness trace † | The executed steps a counterexample's failing clause or trap depends on, replayed through the interpreter and attached to the diagnostic (ADR-047). | `exp = 1100` at `(+ now 1000)` |
| Replay status † | Whether a witness trace reproduced the reported outcome: `reproduced`, `trap_first` (a trap was reached first) or `not_reproduced` (a TCB defect). | `reproduced` |
| Solver-chosen value † | A value the replay took from the Z3 model rather than computing: a called spec's result, a provider operation's result or a parallel-map result. | `sig` from `hmac_sha256` |
| Trap site table † | The table generated into a release binary that maps each trap site to its spec, file, line and column (ADR-048). | `site 3 → Auth::generate_token auth/generate_token.opq:3:13` |
| Call chain † | The spec calls active when a release binary failed, outermost first; reported only by builds with `release.call_chain = true` (ADR-048). | `Main::run → Auth::generate_token` |
| Vacuous contract † | A contract whose `requires` no input satisfies, or whose `requires` and `ensures` no input–result pair satisfies; rejected with `VacuousContract` (ADR-052). | `requires x > 5 && x < 3` |
| Effective evidence † | The weakest evidence level across an accepted implementation and every implementation it transitively calls, computed when reported (ADR-053). | `proved`, effective `tested` |
| Known-answer vector † | A fixed argument tuple and expected result, taken from a standard, against which `cprimec runtime build` checks a `deterministic` operation (ADR-054). | RFC 4231 test case 1 |
| Call outcome † | How a call ends: returns, traps, exceeds a resource limit, provider fails, or diverges (ADR-024). | trap `Overflow` → exit 3 |
| Concrete counterexample † | A counterexample whose violation recurs with real `deterministic` providers and accepted callee implementations (ADR-055). | wrong expiry in `generate_token` |
| Abstract counterexample † | A counterexample valid in the verifier's model that did not recur, or could not be run, concretely; carries a reason (ADR-055). | an all-zero `hmac_sha256` result |
